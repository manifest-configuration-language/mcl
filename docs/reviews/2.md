さらにブラウザ SDK のリクエストにはパラメータが含まれず、WASM 側もパラメータなしの評価 API を呼んでいます。

- [`packages/browser/src/index.js`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/packages/browser/src/index.js?utm_source=chatgpt.com#L405-L570)[— execute](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/packages/browser/src/index.js?utm_source=chatgpt.com#L405-L570)

### P1 — `let` の出所情報追加が共有データを変更し、値のサイズに比例して遅くなる

コード上で、共有データの変更が起こり得る構造を確認しました。

[`typed_ir_evaluate.go`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/typed_ir_evaluate.go?utm_source=chatgpt.com#L114-L145) の変数参照は、既存の `RuntimeValue` を返します。Map や List は内部にスライスを持つため、このコピーだけでは子要素の格納領域を分離できません。

一方、[`eval.go`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/eval.go?utm_source=chatgpt.com#L441-L468) は `let` の評価ごとに `addRuntimeDependencySourceLocation` を呼び、[同ファイルの再帰処理](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/eval.go?utm_source=chatgpt.com#L706-L726) が Map・List・Node の子要素の `SourceLocations` を更新しています。

```
let original =
  metadata:
    name: "api"

let alias = original
```

この場合、`alias` の出所情報を追加するための書き込みが、`original` と共有している子要素にも及び得ます。

Manifest の値そのものを書き換えるわけではありませんが、参照元の診断情報が後続の `let` に影響される可能性があります。さらに、大きな値を参照するたびに全子要素を再帰走査するため、共通設定を何度も再利用する MCL の典型的な使い方で無駄が増えます。

改善策: `let` ごとの出所情報を値グラフ全体へ書き込む設計をやめ、参照・式の評価境界に紐付く不変の provenance 情報として保持します。必要な診断を生成する際に、参照元と利用箇所の情報を統合する方式が適切です。

これにより、共有値の不変性、診断の正確性、評価時の性能を同時に改善できます。

補足：上のコード例の `emit:` は現行 MCL の構文ではありません。正しくは `let config =` で Map を定義し、`emit config` で出力します。以降のコード例は現行構文と変更提案を明確に区別します。

### P1 — Kubernetes Schema 検証が nullable な値を誤って削除する

判定：実装ロジック上の不整合。

対象：[`internal/k8sschema/schema.go:60–171`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/k8sschema/schema.go?utm_source=chatgpt.com#L60-L171)

新しく追加された `omitNullObjectFields()` は、Schema にプロパティが定義されている場合、その値が `null` なら無条件に削除します。

```
if field == nil && len(propertySchemas) > 0 {
    continue
}
```

しかし `null` を許容することと、プロパティを省略できることは別です。

例えば、次の JSON Schema において、`{"field": null}` は有効です。

```
{
  "type": "object",
  "required": ["field"],
  "properties": {
    "field": {
      "type": ["string", "null"]
    }
  }
}
```

現在の前処理はこれを `{}` に変えてしまい、必須フィールドがないという誤った検証エラーを生じさせます。

さらに `propertySchemasFor()` は `oneOf`、`anyOf`、`allOf` の各候補を、実際に選択される分岐を考慮せず走査しています。単に「プロパティ定義が存在するか」で削除を決めるのは、JSON Schema の意味論と一致しません。

現行の Kubernetes 組み込み Schema のどのフィールドが実際に影響を受けるかまでは確認できていません。ただし、アルゴリズム自体の欠陥は明確です。

改善策： `null` を削除する独自の一般化処理を廃止し、Kubernetes OpenAPI の nullable / required に忠実な変換へ変更してください。検証前に変更した入力と、実際に出力する値が食い違う設計も避けたいです。

必要な単体テストは、nullable な必須項目、nullable な任意項目、非 nullable な任意項目、`oneOf` / `anyOf`、`additionalProperties` の組み合わせです。

### P1 — CRD の数値検証に `float64` への情報落ちがある

判定：コード上で確認できる精度損失。

対象：[`internal/engine/crd.go:257–314`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/crd.go?utm_source=chatgpt.com#L257-L314)

MCL は Decimal を十進表現として扱っていますが、CRD 検証用の変換では次の処理を行います。

```
converted, err := strconv.ParseFloat(value.TextValue(), 64)
```

例えば `1.0000000000000001` は `float64` に変換すると `1` に丸められます。

そのため、CRD の制約が `maximum: 1` であっても、MCL が保持している元の数値と Validator に渡した数値で大小関係が変わる可能性があります。

| MCL の値 | `float64` 変換後 | 問題 |
| -------------------- | ------------------ | ----------- |
| `1.0000000000000001` | `1` | 上限超過を見落とす |
| `9007199254740993.0` | `9007199254740992` | 整数部分の精度を失う |
| 極端に小さい Decimal | `0` になり得る | 下限・非ゼロ判定に影響 |

Kubernetes 側の実際のデコードや Validator の数値表現も確認する必要がありますが、MCL が正確に保持していた値を検証直前に丸めることは、少なくとも安全な設計ではありません。

改善策： まず正確な値と変換後の値が一致するかを検査し、情報落ちが起こる場合は黙って検証を続けずエラーにします。採用する Kubernetes Validator が `json.Number` 等を扱えるなら、その経路を優先してください。

すべての数値ライブラリを自作し直す必要はありません。現在利用している Decimal と Kubernetes の既存 Validator の境界に、厳密な変換条件を設定すればよいです。

### P1 — `mergeByKey()` が存在しないキーを自動追加する

判定：仕様上の安全性問題。

対象：[`internal/engine/stdlib.go:554–616`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/stdlib.go?utm_source=chatgpt.com#L554-L616)

`mergeByKey()` は、対応するキーが見つかった場合は既存要素をマージします。しかし、見つからなかった場合は次の処理になります。

```
if !found {
    // ...
    result.List = append(result.List, override)
}
```

これは upsert としては正しい挙動ですが、既存 Kubernetes Container の設定を更新したい場面では危険です。

例えば `api` コンテナのイメージを変更したいのに、誤って `aip` と書いた場合、エラーにならず新しいコンテナが追加されます。

```
# 本当は name: "api" を更新したい
let overrides =
  - name: "aip"
    image: "example.com/api:v2"
```

改善策： 破壊的変更を許容するなら、`mergeByKey()` は存在しないキーをエラーにする方が安全です。

新しい要素を追加したいときは、すでに存在する `concat()` を明示的に使えます。新しい組み込み関数を増やさず、既存の機能だけで「更新」と「追加」を区別できます。

この変更は、Manifest の誤記検出と標準ライブラリの意味の明確化の両方に効きます。

### P1 — 実行パラメータが String 固定で、数値・Bool の設定を自然に記述できない

判定：言語仕様の機能不足。

対象：[`internal/engine/stdlib.go:240–254`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/stdlib.go?utm_source=chatgpt.com#L240-L254)

`context.parameter()` は、すべての引数値を String として返します。

そのため次のような記述は、`replicas` に String を設定することになってしまいます。

```
import "std:context" as context

let replicas = context.parameter("replicas")

let deployment =
  apiVersion: "apps/v1"
  kind: "Deployment"
  metadata:
    name: "api"
  spec:
    replicas: replicas
    # ...
```

現在の標準ライブラリには、String を Int や Bool に変換する組み込み関数もありません。

実行時の構成変更は Kubernetes マニフェストの基本的な用途なので、これは使い勝手に直接影響します。

また、[`parseParameters()`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/cmd/mcl/main.go?utm_source=chatgpt.com#L448-L463) は重複した名前を拒否しますが、ソース側で一度も参照されないパラメータを拒否しません。

存在しないパラメータを指定しても、エラーにならず、設定が変更されたと誤解する可能性があります。

#### 推奨する言語仕様の変更

`context.parameter()` を主な入力方式とするのではなく、明示的なパラメータ宣言を導入することを推奨します。

以下は提案する新構文であり、現在の MCL では使えません。

```

param environment: "dev" | "staging" | "prod" = "dev"
param replicas: Int = 2
param enableMetrics: Bool = true

let config =
  apiVersion: "v1"
  kind: "ConfigMap"
  metadata:
    name: environment
  data:
    enabled: if enableMetrics: "true" else: "false"

emit config

```

パラメータの名前・型・デフォルト値・許容値を宣言すれば、CLI と WASM の入力定義も共通化できます。

さらに、未宣言パラメータ、必須値の不足、型不一致、enum 範囲外を評価開始時に検出できます。暗黙的な環境変数や自動的な型変換は導入しない方が安全です。

### P1 — 十進数と整数の除算が暗黙に精度を失う

判定：現在の仕様は決定的だが、明確性に改善余地がある。

対象：[`internal/engine/eval.go:1125–1212`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/eval.go?utm_source=chatgpt.com#L1125-L1212)

現在の実装では、Int の除算には `big.Int.Quo`、Decimal の除算には `DivRound(..., 16)` が使われます。

| 式 | 現在の意味 | 気になる点 |
| ----------- | ------------ | ------------ |
| `5 / 2` | 整数除算によって `2` | 小数部分が失われる |
| `5.0 / 2.0` | `2.5` | 型によって結果が異なる |
| `1.0 / 3.0` | 小数第16位まで丸め | 丸めが式から読み取れない |

Go などのプログラミング言語では整数除算は一般的ですが、MCL は主に設定値を宣言する言語です。記述した数値が意図せず丸められることのデメリットが大きいと考えます。

推奨： `/` は小数を表せる演算として扱い、整数除算・丸めは明示的な関数に分離してください。無限小数となる場合の扱いも、精度と丸めモードを指定するか、正確に表せない除算をエラーにするか、言語仕様として固定する必要があります。

ただし、こちらはバグ修正ではなく互換性を破壊する言語設計上の判断です。

## 2. 性能・保守性に関する追加指摘

### P2 — Kubernetes Schema の `null` 処理がフィールドごとに Schema を再走査する

対象：[`internal/k8sschema/schema.go:60–171`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/k8sschema/schema.go?utm_source=chatgpt.com#L60-L171)

`propertySchemasFor()` と `itemSchemasFor()` は、呼び出されるたびに `visited` Map を作り、`Ref`、`AllOf`、`AnyOf`、`OneOf` を再帰的に調べます。

つまり、Manifest 側の各フィールドについて Schema の探索処理が繰り返されます。大きな Manifest や複雑な CRD に近い Schema では、余分な割り当てと走査が増えます。

改善策： 上述の `null` 正規化方式自体の見直しを優先します。その処理がなお必要なら、コンパイル済み Schema からフィールドごとの規則を一度だけ導出して再利用してください。

正確性を修正せずに現在の再帰処理だけをキャッシュするのは推奨しません。

### P2 — `std:list.union()` は深い比較を繰り返す

対象：[`internal/engine/stdlib.go:442–460`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/engine/stdlib.go?utm_source=chatgpt.com#L442-L460)

重複排除は、追加しようとする各要素を、結果リストの全要素と `equalRuntimeValues()` で比較しています。

```
if deduplicate &&
    slices.ContainsFunc(result.List, func(existing RuntimeValue) bool {
        return equalRuntimeValues(existing, item)
    }) {
    continue
}
```

比較回数は最悪で二次的に増えます。Map や List を比較する場合は、1回の比較自体も安価ではありません。

改善策： String、Int、Bool などのスカラーは型付きキーを使って重複判定し、複合値は正規化したハッシュと厳密比較を組み合わせる方法が考えられます。

ただし、巨大な構造的ハッシュ機構を新たに自作するのはメンテナンスコストと釣り合わない可能性があります。まずスカラーだけを最適化する設計が妥当です。

### P2 — LSP の位置変換が既存の共通実装と重複している

対象：

- [`internal/lsp/documents.go:109–139`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/lsp/documents.go?utm_source=chatgpt.com#L109-L139)
- [`internal/sourceindex/index.go:20–100`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/internal/sourceindex/index.go?utm_source=chatgpt.com#L20-L100)

`offsetAtUTF16()` は指定された行まで改行を探して進み、さらに行内を Rune 列に変換しています。

一方、`sourceindex.Index` にはすでに UTF-16 位置をバイトオフセットに変換する `OffsetAt()` が実装されています。

これは同じ責務を持つ二つの処理が存在する状態です。

改善策： LSP の位置変換を `sourceindex` に一本化し、ドキュメントごとの Index を管理します。

単に毎回 `sourceindex.New()` するだけでは全体走査が残るため、変更後の Index を更新または再構築する場所まで共通化するのが適切です。

狙いは微小な速度改善だけでなく、UTF-16、CRLF、Unicode の境界処理が複数実装に分散することを防ぐ点にあります。

### P2 — npm パッケージの検証はファイルの存在確認が中心

対象：[`scripts/verify-installed-packages.mjs`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/scripts/verify-installed-packages.mjs?utm_source=chatgpt.com)

このスクリプトはインストール済みパッケージの `package.json` を読み、指定ファイルの存在・非空・バージョンの一致を確認します。

目的に対して簡潔ですが、現状では `package.json` の `exports` が誤っていても、ファイルそのものが存在すれば検査を通過できます。

改善策： インストール済みパッケージをその公開 API 名で `import()` できることを確認します。既存のパッケージ検証に数行追加するだけで十分で、新たなテスト基盤は不要です。

### P2 — リリースタグの独自正規表現が SemVer と一致していない

対象：

- [`.github/workflows/release.yml`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/.github/workflows/release.yml?utm_source=chatgpt.com)
- [`.github/workflows/release-candidate.yml`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/.github/workflows/release-candidate.yml?utm_source=chatgpt.com)

両方で類似したタグ検証ロジックを Bash の正規表現で実装しています。

例えば正規表現は `v1.2.3.foo` のような SemVer として不正な表記を許容します。一方、SemVer の正式な build metadata である `+build.1` などには対応していません。

改善策： バージョン文字列の妥当性は標準的な SemVer 実装で検査し、タグと二つの `package.json` のバージョン一致を一つの小さな検証処理にまとめます。自前の正規表現を二箇所で保守する必要はありません。

なお、既存レビューにあるリリース処理の Bash 全般や draft の扱いに関する提案は、ここでは繰り返していません。

### P3 — README が存在しない mise タスクを案内している

対象：

- [`README.md`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/README.md?utm_source=chatgpt.com)
- [`mise.toml`](https://github.com/manifest-configuration-language/mcl/blob/04fdad2a698679c826261406d339bfbbe4c10751/mise.toml?utm_source=chatgpt.com)

README には次の説明があります。

```
mise run release:cli
```

しかし現行 `mise.toml` に `release:cli` タスクはありません。存在するのは `release:wasm`、`release:reference`、`release:package` などです。

改善策： README の記述を修正します。不要なタスクを増やすより、すでに記載されている `go build -o ./mcl ./cmd/mcl` を開発用 CLI ビルドの標準手順として案内する方が簡潔です。

## 3. 言語仕様として、さらに優先して決めたいこと

今回コードを確認して、MCL の強みとして残すべきものと、破壊的に改善するべきものがより明確になりました。

### 残すべき設計

`let` / `fn` による値の構築、`with` による明示的な合成、`node` / `ref` による参照、`emit` による出力、`rule` / `validate` による検証という責務分離は維持すべきです。

特に レンダリングと検証を別の操作として表現していること は重要です。ルールが Manifest を暗黙に変更する機能は導入しない方がよいです。

また、Kubernetes 固有のリストを `with` が暗黙に Strategic Merge する仕様にも反対です。リストの更新は、更新対象と更新方法を明示するべきです。

### 破壊的変更を許容して導入したい設計

1\. `param` 宣言を導入する

型付きパラメータと許容値を言語の一部にし、入力値の不足・誤記・型不一致を評価前に検出します。`context.parameter()` による暗黙的な文字列入力を主役にしない設計です。

2\. リスト操作で更新と追加を区別する

`mergeByKey()` を厳密な更新として扱い、存在しないキーをエラーにします。追加は既存の `concat()` で明示すればよく、余計な構文も不要です。

3\. 数値の精度規則を統一する

十進数を正確に表現する方針と、除算・JSON 変換・Kubernetes 検証での精度損失を矛盾させない仕様にします。暗黙の丸めは最小限に抑えます。

4\. Schema に基づく型と Validator の意味を一致させる

nullable、required、数値の制約、`x-kubernetes-int-or-string` などについて、静的解析と実行時検証が異なる解釈をしないよう共通の規則に集約します。

5\. Value と provenance を分離する

構築した値を共有しても、別の `let` の評価によって診断情報が変わらないようにします。性能改善と意味論の単純化を兼ねます。

### `with` の使い勝手について

Kubernetes Manifest の実用性という観点では、`with` の基本仕様を難しくする必要はありません。

Map は再帰的に合成し、List は全体置換する。特定要素だけ変更したい場合は、既存の `list.mergeByKey()` を使う。この考え方で十分に柔軟です。

ただし、現在の `mergeByKey()` は存在しないキーを追加するため、ここだけは厳格化した方がよいです。

重要なのは、見た目が YAML に近いだけでなく、変更したときに何が起こるかを構文から予測できることです。

## 4. メンテナンスコストを最小化する最終方針

既存レビューですでに扱われている Treap、Helm Hook、Typed IR の重複、自前 Git 取得処理、WASM サイズなどは、今回の新規指摘には含めていません。

それらを前提としたうえで、今回追加で見つけた問題を解決するために、技術スタック全体を変更する必要はないと考えます。

| 領域             | 推奨                                            |
| -------------- | --------------------------------------------- |
| 言語ランタイム        | Go を維持                                        |
| パラメータ          | 型付きの言語宣言と共通評価オプション                            |
| 出所情報           | 不変データと参照関係で保持                                 |
| 数値             | 現在の Decimal を基盤として精度境界を厳密化                    |
| Kubernetes 検証  | Kubernetes 公式ライブラリと JSON Schema Validator を利用 |
| LSP 位置変換       | `internal/sourceindex` に一本化                   |
| 標準ライブラリ        | 既存関数の意味を明確化し、追加は必要最小限                         |
| GitHub Actions | 標準のバージョン解析・パッケージ管理機能を利用                       |
| npm パッケージ      | 既存の検証スクリプトに公開 API の確認を追加                      |

Kubernetes / Helm / Kustomize の既存 SDK を直接利用できることを考えると、Go から Rust や TypeScript へ全面移行しても、得られる利益より新たな境界・再実装コストが大きいと思います。

## 5. 改善の優先順位

最優先：正確性と安全性

P1

`null` 正規化、数値精度、`let` の共有値変更、実行パラメータの不整合、`mergeByKey()` の厳格化

これらは、意図した Manifest が生成されない、検証の結果が正しくない、あるいは利用者が変更の影響を誤解する原因になります。

次点：言語仕様の確定

P1–P2

型付き `param`、算術の丸め規則、Schema 型と Validator の一貫性

破壊的変更を許容できる現段階で決めておく価値が高い部分です。

その後：単純化と性能

P2–P3

Schema 探索の重複、LSP 位置変換の共通化、リスト重複排除、Actions の正規表現、パッケージ検証、README

性能改善は、複雑な自前最適化を導入するのではなく、不要な再走査・重複実装をなくすことを優先します。

## 結論

今回、既存レビューと重複しない問題として特に重要だったのは、`let` の診断情報が共有値を変更し得ること、検証時の `null` と Decimal の扱い、パラメータ機能の実行環境間の不統一、`mergeByKey()` の暗黙的な追加です。

いずれも Kubernetes Manifest を安全・簡潔・予測可能に記述するという MCL の目的に直結しています。

最終的には、複雑な機能を追加するよりも、入力は型付きで明示する、合成は非破壊で明示する、参照は最終的な存在を保証する、検証は元の値を正確に評価する、という原則を徹底した設計にするのが最もよい方向だと考えます。

既存レビューで指摘済みの問題も含めた総合評価では、言語の方向性を変える必要はなく、曖昧な意味論と実装間の不整合を減らすことが、今の MCL を長期的に優れた言語へ進化させるうえで最も重要です。

# MCL リポジトリ徹底レビュー

対象：[manifest-configuration-language/mcl](https://github.com/manifest-configuration-language/mcl/tree/0d9e935298a905dedd2b5c9f763d1d255e81f858?utm_source=chatgpt.com) · `main` · `0d9e935` · 2026年11月3日

現行コードを確認したうえで、最も重視すべきなのは 「Manifest を生成できること」と「安全で正しい Manifest だと保証できること」の差です。

MCL はすでに、型付き評価、遅延参照、Schema、Contract、Helm/Kustomize、ソース位置追跡まで実装しています。基本的な技術選択は妥当です。一方で、検証の対象選択、未知の Kubernetes リソース、Schema の扱いには、言語が目指す安全性を弱める箇所があります。

以下、コード上で確認した動作、そこから生じるリスク、推奨する修正を区別して記載します。破壊的変更を前提とします。

## 最優先で修正したい問題

### P0-1. 未知の Kubernetes GVK が検証されずに通過する

確認箇所： [internal/engine/builtin_kubernetes_validation.go L10–45](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/builtin_kubernetes_validation.go?utm_source=chatgpt.com#L10-L45)

現在は組み込み Schema が見つからなければ、そのリソースの組み込み Schema 検証をスキップします。

```
if !k8sschema.HasBuiltinSchema(apiVersion, identity.kind) {
    return nil
}
```

この動作は、未知の CRD を柔軟に扱える一方、`apiVersion` や `kind` の誤記、対象バージョンとの不一致、Schema 未登録のカスタムリソースを見逃し得ます。

推奨修正： 検証状態を `Validated`、`UnknownSchema`、`Invalid` のように明示的に区別してください。Kubernetes Manifest としての厳格な検証を要求した場合、`UnknownSchema` は成功とみなさない設計にします。外部 CRD についてはローカル Schema を明示的に登録できるようにし、未知の型を許容する選択も明示的に行わせます。

重要なのは、「未知のリソースをサポートしない」ことではなく、検証できなかったものを検証済みと誤認させないことです。

### P0-2. `validate each descendants(...)` が検証すべき対象を見落とし得る

確認箇所： [internal/engine/references.go L285–332](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/references.go?utm_source=chatgpt.com#L285-L332)

型に由来する情報がない候補について、現在は次の判定で検証対象を選びます。

```
selected = checkRuntimeType(candidate, *validation.QueryType, validation.Types, make(map[string]bool)) == nil
```

これは非常に重要な設計上の問題です。

例えば、あるオブジェクトが Kubernetes の Container に相当する場所に存在していても、そのオブジェクト自身に型不整合があれば `Container` に一致しないと判断され、Container 用 Rule の対象から外れる可能性があります。

つまり、型が不正だから検証対象から除外されるという逆転が起こり得ます。

現在の `minMatches` の既定値は1なので、別の正常な Container が1個でも見つかれば、対象漏れを検出できない場合があります。

推奨修正： 「何のリソース・フィールドか」という型の所属情報と、「値が型に適合するか」という検証結果を分離します。

Kubernetes Deployment の `spec.template.spec.containers[*]` にある値は、たとえ不正でも Container として分類すべきです。そして型不整合と Security Rule 違反を、それぞれ診断します。

これは Contract システムの根本的な修正として優先します。

### P0-3. 未登録 CRD も最終的に検証をすり抜け得る

確認箇所： [internal/engine/crd.go L39–94](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/crd.go?utm_source=chatgpt.com#L39-L94)

現在の実装は、Bundle に含まれる CRD から Schema を収集し、対応するカスタムリソースを検証しています。これは有用です。

しかし、Bundle 内に対応する CRD がないと `registered` が見つからず、検証処理がスキップされます。外部の Schema が組み込み Schema として見つからなければ、前述の問題と重なります。

推奨修正： CRD Schema の取得元を、同じ Bundle に含まれる CRD に限定しないことです。外部 Schema を明示的な依存関係として登録でき、最終検証が必ずその登録情報を参照する仕組みにします。静的な Schema と実行中のクラスタの状態は混同しません。

### P1-1. Kubernetes Schema からの静的型生成が、未知のフィールドに寛容すぎる

確認箇所： [internal/k8sschema/schema.go L253–305](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/k8sschema/schema.go?utm_source=chatgpt.com#L253-L305)

現在のオブジェクト型生成では、`additionalProperties` が明示されていないと OpenRecord として扱います。

```
open := schema.AdditionalProperties == nil ||
    schema.AdditionalProperties.Allows ||
    schema.AdditionalProperties.Schema != nil
```

JSON Schema としての `additionalProperties` の意味はありますが、Kubernetes Manifest 作成言語としては、通常の構造化フィールドの誤記を積極的に検出する必要があります。

例えば `image` を `imag` と書いた場合に、対象 Schema がそのフィールドを閉じていないという理由で許可するのは望ましくありません。

推奨修正： 汎用 JSON Schema の解釈と、Kubernetes 構造型の未知フィールド検査を分離します。通常の Kubernetes オブジェクトでは未知フィールドを検出し、`metadata.labels`、`annotations`、ConfigMap の `data`、Schema 上で自由な Map、未知フィールド保持を許可した CRD 領域は適切に例外扱いします。

`additionalProperties` の意味を勝手に書き換えるのではなく、Kubernetes 用の追加の静的検査として実装するのが適切です。

### P0-4. `clone()` が再帰的な関数のクロージャで無限再帰する可能性

確認箇所： [internal/engine/eval.go L509–514](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/eval.go?utm_source=chatgpt.com#L509-L514)、[internal/engine/runtime_value.go L449–634](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/runtime_value.go?utm_source=chatgpt.com#L449-L634)

これは実装上の重大な疑いです。

名前付き関数は、自分自身をクロージャのスコープに格納しています。

```
lambda.Lambda.Scope[declaration.Name] = lambda
```

一方、`cloneRuntimeValueGraphInto()` は Lambda のスコープを再帰的に複製しますが、訪問済み Lambda を記録する仕組みがありません。

```
for name, captured := range lambda.Scope {
    lambda.Scope[name] = cloneRuntimeValueGraphInto(captured, identities, references)
}
```

そのため、例えば次の入力は、型推論上 `clone()` が関数を拒否していないことも踏まえると、再帰的なコピーに入ると考えられます。

```
fn identity(x: Int) -> Int =
  x

let copied = clone(identity)

emit "done"
```

`clone()` の静的型推論は引数の型をそのまま返しています。関数型を明示的に拒否していません。[該当実装](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/static_expr_calls.go?utm_source=chatgpt.com#L399-L405)

推奨修正： `clone()` は原則としてシリアライズ可能なデータ値と `Node<T>` に限定します。関数、Rule、内部的な遅延計算はコピー対象として拒否するか、オブジェクトの同一性を記録して循環グラフを安全にコピーする仕様を明示します。

少なくとも、スタックオーバーフローではなく通常の MCL 診断を返せる必要があります。

この問題はソースから推定できる実行経路が具体的ですが、実際のクラッシュ再現はまだ行えていません。

### P1-2. `clone()` のサイズ計算が、実際のコピーより先に大量の再帰を行う

確認箇所： [internal/engine/runtime_value.go L342–428](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/runtime_value.go?utm_source=chatgpt.com#L342-L428)

`cloneRuntimeValueGraphWithBudget()` は最初に `runtimeValueGraphSize()` で値グラフ全体を走査し、その後でコピーします。

クロージャなどの循環はサイズ計算時には一定程度検出していますが、同じ部分グラフを複数箇所から参照するケースで、探索結果をグローバルにメモ化していません。

共有された大きな値が複数のスコープに捕捉される場合、実際の値のサイズに対して計算量が膨らむ可能性があります。

推奨修正： 循環を検出する `active` と、計算済みの部分グラフを記録する `visited` を分け、サイズ計算とコピーの両方で同じグラフの意味論を使用します。さらに、コピー中にも予算を消費させ、事前の全量走査に依存しない安全性を確保します。

## Helm / Kustomize：レンダリング以外の責務を持ちすぎている

### P1-3. Helm Hook annotation を出力 Manifest から取り除いている

確認箇所： [internal/engine/helm.go L372–465](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/helm.go?utm_source=chatgpt.com#L372-L465)

現在のコードは `helm.sh/hook` などを解析した後、対象 annotation を元の Map から削除します。

```
filtered := annotations.Map[:0]
for _, entry := range annotations.Map {
    if !isHelmHookAnnotation(entry.Key) {
        filtered = append(filtered, entry)
    }
}
annotations.Map = filtered
```

MCL の責務を Helm Chart から Manifest をレンダリングすることだけに限定するなら、この変更は不要であり、予想外です。

レンダリングされた内容が Helm のテンプレート結果と一致しなくなり、Hook の意味も MCL 独自の lifecycle に変換されます。

さらに、`create`、`update`、`delete`、`rollback`、`verify` の phase を解釈する処理が、[internal/engine/render.go L549–686](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/render.go?utm_source=chatgpt.com#L549-L686) に実装されています。

推奨修正： Helm Hook annotation は入力どおり保持し、Helm アダプターは Manifest の生成に専念させます。ライフサイクルの表現が本当に必要なら、Manifest の内容と分離された汎用的なメタデータに限定し、Helm の管理動作を MCL 内で再現しないことを推奨します。

これは単なるコード削減ではなく、言語の責務を明確にする破壊的変更です。

### P1-4. Helm の危険な関数を手作業のブラックリストで無効化している

確認箇所： [internal/helmrender/helmrender.go L438–470](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/helmrender/helmrender.go?utm_source=chatgpt.com#L438-L470)

`lookup`、`now`、`randAlphaNum`、証明書生成などを無効化している方針自体は適切です。

しかし現在は、危険だと認識した関数名を `hermeticFunctions()` に手作業で列挙しています。

Helm や Sprig に新しい関数が追加された場合、その関数が安全かどうかを MCL 側で確認する仕組みがなければ、将来のアップデートで非決定的な処理が入り込む余地があります。

推奨修正： 許可した関数だけを使用できる allowlist 方式を第一候補にします。Helm SDK で完全な allowlist が難しい場合でも、アップグレード時に公開テンプレート関数の集合と MCL の許可・禁止集合の差分を検出し、未知の関数を自動的に禁止する仕組みが必要です。

既存の SDK を捨ててテンプレートエンジンを自作することは推奨しません。

### P1-5. `.helmignore` で除外したファイルも読み込み・サイズ計算している

確認箇所： [internal/helmrender/helmrender.go L472–551](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/helmrender/helmrender.go?utm_source=chatgpt.com#L472-L551)

`loadChartFS()` は `.helmignore` を読みますが、ファイルの内容読み込みとサイズ加算を行った後で、除外対象かどうかを判定しています。

そのため、Chart の生成に関係しない大きなファイルがあっても、読み込みコストを負担し、場合によっては `maxChartBytes` に到達します。

また、無視されたファイルの内容もキャッシュキーの構築に使われるため、レンダリング結果が変化しない変更でもキャッシュが失効します。

推奨修正： 除外対象を先に判定し、無視するディレクトリは `fs.SkipDir` で走査自体を省きます。キャッシュキーも、実際に Helm Chart の入力になるファイルから計算します。

これは既存の仕様を維持したまま実施できる、比較的明確な性能改善です。

## パフォーマンス：評価器と WASM の構造を見直す

### P1-6. 遅延参照のための独自 Treap は、保守コストが高い

確認箇所： [internal/engine/runtime_bundle_index.go](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/runtime_bundle_index.go?utm_source=chatgpt.com)

このファイルでは、順序統計 Treap によって最終 Bundle の値列を管理し、遅延値の解決に伴う部分木の置換を高速化しています。

技術的には面白い設計です。単純に全体を再走査しないための工夫も確認できます。

ただし、現在は次の複数の状態を同期させています。

- Treap 上の順序と部分木サイズ
- `RuntimeValue` ポインタから出現箇所への索引
- Node identity から出現箇所への索引
- 親子関係と Artifact の所属
- 評価予算とノード数制限

これだけの不変条件を、`replaceOccurrence()` と `buildDetachedSubtree()` などの独自処理で維持しています。

特に [L267–320](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/runtime_bundle_index.go?utm_source=chatgpt.com#L267-L320) では、置換後に `index.valueCount` を評価ステップへ加算します。

```
state.Budget.steps += index.valueCount
```

つまり、遅延値の置換が M 回、Bundle の値数が N 個の場合、評価予算の消費量が概念的に O(N×M) まで増える可能性があります。

これは実際の置換処理が効率的でも、評価予算のために正常な入力を拒否する要因になり得ます。

推奨修正： 最初に、独立した `ResolutionPlan` を作り、Node identity・依存関係・未解決式を1つのモデルで管理する設計へ整理します。まず DFS と明示的な依存グラフで正しさを保証し、Treap が必要な規模・操作だけに高速化を限定します。

Treap を直ちに削除すべきと断定するものではありません。既存のベンチマークで有意な改善があれば残す価値はあります。ただし、高速化のために言語の正しさや診断を難しくする構造は避けるべきです。

### P1-7. WebAssembly のサイズが非常に大きい

確認箇所： [packages/browser/performance-profile.md](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/packages/browser/performance-profile.md?utm_source=chatgpt.com)

リポジトリ自身が、2026年10月22日時点の WASM サイズを計測しています。

非圧縮 WASM

# 107.84 MiB

gzip 圧縮後

# 18.69 MiB

過去の計測コミット `3eeb4806` における値であり、今回の HEAD で再計測したものではありません。

関数本体サイズの計測内訳では、`k8s.io/api` だけで約22.47 MiB、CEL 関連で約3.60 MiB を占めています。

ただし、これらの数値は依存パッケージの寄与を分類したものであり、その依存を削除すると同じサイズだけ縮小することを意味しません。

推奨修正： Go コンパイラと単一の言語実装は維持したまま、WASM の提供単位を用途別に分ける方向が最も合理的です。

| WASM | 主な機能 | 目的 |
| ---- | ----------------------------------------- | ------------- |
| Core | 構文解析、整形、基本的な解析、軽量な補完 | エディタ起動時の低コスト化 |
| Full | 型付き評価、参照解決、Schema、Helm/Kustomize、最終レンダリング | 明示的な実行時に読み込む |

ただし、単純にバイナリを2つ作るだけでは、依存関係が同じなら小さくなりません。Go の import 境界と内部パッケージを整理し、Core が Kubernetes API 全体を引き込まない構造にする必要があります。

同じリポジトリ内の別エントリーポイントとするだけで十分であり、新しいリポジトリや別言語への移植は不要です。

### P1-8. スキーマ解析・型推論・評価の表現が複数に分散している

主な確認箇所： [internal/engine/static_types.go](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/static_types.go?utm_source=chatgpt.com)、[typed_ir_typecheck.go](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/typed_ir_typecheck.go?utm_source=chatgpt.com)、[typed_ir_evaluate.go](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/typed_ir_evaluate.go?utm_source=chatgpt.com)、[runtime_value.go](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/runtime_value.go?utm_source=chatgpt.com)

現状は、静的な式の型推論、Typed IR の構築、特殊化、実行時値、Deferred continuation がそれぞれかなり大きな実装を持ちます。

遅延参照と型付き関数を両立するために必要な部分はありますが、同じ演算子の規則や型情報を複数の段階で扱うことになり、将来の言語仕様変更のコストが高くなります。

長期的には、以下の単方向パイプラインに整理するのがよいです。

AST

Typed IR

不変の評価結果・遅延参照グラフ

参照解決済み Bundle

Schema・Contract 検証 → シリアライズ

型規則は可能な限り1か所に集約し、Typed IR を作成した後の評価器が再び静的型推論を行わない設計を目指します。

現在のコードを全廃して書き直すより、重複している処理を段階的に取り除くリファクタリングが適切です。

## 追加の正確性・安全性レビュー

### P1-9. CRD の CEL 検証に呼び出し元の Context が渡っていない

確認箇所： [internal/engine/crd.go L81–90](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/crd.go?utm_source=chatgpt.com#L81-L90)

```
celErrors, _ := registered.cel.Validate(
    context.Background(),
    field.NewPath("resource"),
    registered.structural,
    instance,
    nil,
    int64(celconfig.PerCallLimit),

```

`context.Background()` を使用すると、呼び出し元のキャンセルや期限を CEL 検証へ伝播できません。

改善策： `validateRuntimeBundleCustomResources()` に Context を渡し、CEL の評価にも伝播させます。また、複数リソースに対する CEL 検証全体の予算も管理します。

### P1-10. Kubernetes 固有の List 制約が Schema 検証で十分に扱われていない

確認箇所： [internal/k8sschema/schema.go L34–121](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/k8sschema/schema.go?utm_source=chatgpt.com#L34-L121)

組み込み Kubernetes Schema は JSON Schema Validator に変換して検証していますが、Kubernetes 独自の `x-kubernetes-list-type` や `x-kubernetes-list-map-keys` の意味は、その処理だけでは完全に検証できません。

一方、CRD の検証では [listtype.ValidateListSetsAndMaps](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/crd.go?utm_source=chatgpt.com#L81-L84) が明示的に呼ばれています。

この差は統一すべきです。

改善策： 組み込みリソースと CRD で共通の Kubernetes Schema 検証パイプラインを用意し、List の map/set トポロジー検証を共通化します。

なお、構造的な Schema 検証だけで Kubernetes API Server の全検証を再現できるわけではありません。例えば Deployment の selector と Pod template の labels の整合性など、別の意味的制約が存在します。独自 Validator を際限なく増やすのではなく、MCL が保証する範囲を明文化するべきです。

### P1-11. `mcl.lock` がツールチェーンのパッチ更新で使えなくなる

確認箇所： [internal/dependency/lock.go L385–391](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/dependency/lock.go?utm_source=chatgpt.com#L385-L391)、[internal/engine/version.go L43–66](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/version.go?utm_source=chatgpt.com#L43-L66)

現在の互換性判定は、MCL と Go のバージョンを完全一致で比較しています。

```
return identity.MCL == locked.MCL &&
    identity.Go == locked.Go &&
    identity.Helm == locked.Helm &&
    identity.KustomizeAPI == locked.KustomizeAPI &&
    identity.KustomizeKYAML == locked.KustomizeKYAML
```

つまり Go のパッチバージョンや MCL のバージョンが変わるだけで、外部 Manifest の SHA-256 が同じであってもロックファイルが非互換になります。

再現可能性を重視する意図は理解できますが、依存関係の固定と処理系バージョンの固定が混在しています。

改善策： ロックファイルの責務を「外部入力の固定」に限定します。コンパイラやレンダラーのバージョンは評価結果のキャッシュキーやビルド情報で追跡し、依存ロックの無効化とは分離します。

また、Helm/Kustomize のバージョン変更による出力差分は必要に応じて検出しますが、毎回すべての依存を再取得する必要はありません。

### P1-12. `go install @latest` と配布バイナリで MCL のバージョン表示が異なる可能性

確認箇所： [internal/engine/version.go L10–16](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/version.go?utm_source=chatgpt.com#L10-L16)、[cmd/mcl/main.go L400–416](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/cmd/mcl/main.go?utm_source=chatgpt.com#L400-L416)

現在の既定値は：

```
var ToolchainVersion = "0.1.0-dev"
```

GoReleaser は `-ldflags -X` でこの値を更新します。しかし README に記載されている `go install ...@latest` では、その ldflags が適用されません。

したがって、実際には公開バージョンをインストールしていても `mcl version` が `0.1.0-dev` と表示される可能性があります。前述の依存ロックの問題にも影響します。

改善策： `debug.ReadBuildInfo()` の `Main.Version` を利用し、Go モジュール経由のインストールではそのバージョンを優先します。GoReleaser の明示バージョンは必要な場合にだけ上書きします。

### P2-2. LSP の順序制御がキャンセル待機に対応していない

確認箇所： [internal/lsp/server.go L54–73](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/lsp/server.go?utm_source=chatgpt.com#L54-L73)

```
<-previous
```

## 言語仕様そのものの改善

コードを見る限り、MCL の基本思想は良い方向に進んでいます。特に、値の定義と `emit`、`rule` / `validate` が分離され、`with` による明示的な合成と、最終 Bundle に対する `ref` 解決が存在する点は維持したいです。

ただし、Kubernetes Manifest を簡潔・安全に記述するという観点では、さらに整理できます。

### 1. 型の記法も YAML に近づける

現在の実例では、構造型を以下のように記述します。

```
type Container = {name: String, securityContext: {allowPrivilegeEscalation: Bool, seccompProfile: {type: String}}}
```

値の構文はインデントベースなのに、型だけ `{}` とカンマが多くなっています。

将来的には、次の形式を標準とすることを推奨します。

```
type Container =
  name: String
  image: String
  ports: List<Port>?
  securityContext:
    allowPrivilegeEscalation: Bool
```

これならデータと型で同じ視覚的な構造を維持できます。型式のインライン表記を完全に禁止するかは別途決める必要がありますが、Formatter が生成する標準形式はブロック型に統一するのがよいでしょう。

### 2. `validate` の対象選択を構造型ではなく、Schema 上の所属で行えるようにする

現状の `descendants(output, Container)` は汎用的ですが、Kubernetes では実際に「Container として使われている場所」を調べたいケースが多いです。

推奨するのは、通常の構造型セレクターに加えて、Schema 上のフィールド位置で選択する方法です。

概念例：

```
validate each descendants(
  output,
  schemaType = kubernetes.Container,
) using hardened
```

ここで `schemaType` は、値が Container 型を満たすかどうかではなく、Kubernetes Schema 上で Container と宣言された位置を選択します。

誤った値が含まれていても検証対象から外れません。

この仕組みを導入するには、レンダリングされた Manifest に対して GVK と Schema を対応付け、子フィールドへ所属型を伝播させる必要があります。

### 3. `emit` の出力種別を明示できるようにする

現在は `emit` が任意の値を扱えるため、Kubernetes リソースではない Map や Scalar も出力できます。

汎用の構成言語としては正しいですが、Kubernetes 用に使用する際には安全性が弱くなります。

そこで、エントリーポイントに出力の種類を宣言できる仕様を推奨します。

例えば：

```
output kubernetes

emit deployment
emit service
```

この宣言がある場合、最終出力は Kubernetes Resource の集合でなければエラーにします。

他の用途向けには `output yaml` や `output json` を提供できます。

これによって、Kubernetes 用の厳格な安全性と汎用性を両立できます。`output kubernetes` は Manifest を変更せず、検証条件と出力形式を決めるだけです。

### 4. `with` はこのまま維持する

[既存のテスト](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/mcl_test.go?utm_source=chatgpt.com#L402-L447) でも、Map の再帰合成と List の置換が明示的に保証されています。

これは維持するべきです。

Kubernetes の strategic merge patch のような、フィールドに応じて List の合成方法が変化する機構を `with` に混ぜないでください。

必要な場合だけ `mergeByKey()` などを明示的に使う設計のほうが、安全で読みやすいです。

### 5. Helm の operation / lifecycle を言語の中心から外す

現行の `lifecycle.attach()`、`before.create`、`after.delete`、`rollback`、`verify` などは、汎用 Manifest 構成言語の必須機能とは言い切れません。

単なるレンダリング以上の概念を MCL が保持することになり、CLI、型、評価、Bundle、Schema、出力にまで複雑さが波及しています。

最もメンテナンス性を重視するなら、MCL の中心機能は 値を構築して検証し、決定的な Manifest を出力することに絞ります。

Helm Hook の対応を残す必要がある場合も、その処理を Helm アダプターの独立した出力メタデータに閉じ込めるべきです。

## 最終的に採用したい技術構成

技術スタックを大幅に変更してもよいという条件ですが、Go から別言語へ全面移行することは推奨しません。

理由は、MCL の難しさが構文解析器そのものより、Kubernetes、Helm、Kustomize、Schema、CEL との正確な連携にあるためです。

Go であれば公式の Kubernetes 関連ライブラリや Helm SDK を直接利用できます。Rust や TypeScript に移行すると、同じ機能を別言語で再実装したり、Go との境界を増やしたりすることになり、目標のメンテナンスコスト削減とは逆方向になる可能性が高いです。

推奨する最終構成は次のとおりです。

| 領域                | 採用する技術                          |
| ----------------- | ------------------------------- |
| コンパイラ・評価器         | Go                              |
| データ処理             | 不変の Typed IR / Runtime Value    |
| YAML              | 既存ライブラリを利用                      |
| Kubernetes Schema | Kubernetes 公式ライブラリと JSON Schema |
| CRD / CEL         | Kubernetes 公式の検証機構              |
| Helm              | Helm SDK、レンダリングに限定              |
| Kustomize         | Kustomize SDK                   |
| LSP               | 既存 JSON-RPC / LSP ライブラリ         |
| Editor grammar    | Lezer + 生成された TextMate          |
| Browser runtime   | Go WASM、必要に応じて Core / Full を分離  |
| CLI               | Cobra                           |
| Build             | mise + GoReleaser + pnpm        |
| Packaging         | 標準ツールを中心に最小限の Node.js           |

## 結論

MCL は、単なる YAML テンプレートエンジンではなく、型、Schema、遅延参照、検証を持った構成言語としてかなりの機能が実装されています。

その一方、現段階では 機能を増やすことより、既存の機能の責務と保証範囲を厳密にすること が最も価値のある改善だと考えます。

特に、未知の Kubernetes リソースをそのまま通す仕様は、[既存テストでも意図的に保証されています](https://github.com/manifest-configuration-language/mcl/blob/0d9e935298a905dedd2b5c9f763d1d255e81f858/internal/engine/mcl_test.go?utm_source=chatgpt.com#L817-L843)。これは偶発的なバグではなく、安全性の目標に合わせて変更すべき言語仕様です。

また、Helm の操作フェーズを MCL の内部に深く取り込む必要性は低いと考えます。ここを切り離せば、評価、Bundle、CLI、テストの多くを簡潔にできるはずです。

目指す状態は次です。

MCL は値を構築する。`emit` は出力を宣言する。`ref` は参照先を保証する。`validate` は最終出力を非破壊で検証する。Helm/Kustomize は外部データを作るだけ。

この原則に沿って、検証の抜け穴と不要な複雑さを減らすことを最優先にします。

なお、今回のレビューは GitHub 上の現行ソース、既存テスト、ビルド設定の読み取りに基づきます。こちらの実行環境ではリポジトリの clone ができなかったため、`go test ./...`、実際のクラッシュ再現、最新 HEAD の性能測定は実施できていません。実行で確認できた不具合と、ソース上から特定した不具合の可能性は区別しています。

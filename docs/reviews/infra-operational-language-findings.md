# 実運用例に基づくMCL設計上の指摘

## Kubernetesリソースの静的型推論

`node:`内で`apiVersion`と`kind`が静的に決まる場合でも、MCLは既知のKubernetes Schemaを構築中の値の型検査に使わず、関数の戻り値も`Map<String, Any>`として扱います。既知のGVKではSchemaから型を推論し、`spec`の構築中に誤ったフィールド名や値の型を検出できる必要があります。CRDは同じ評価で定義されたSchema、または明示的に読み込んだSchemaから型を解決する必要があります。

## リソース検証構文

`validate each descendants(output, Container) using rules.x`は対象を関数呼び出し風の式で指定するため、何を検証するかが初見で分かりにくくなります。検証対象と適用条件を自然に読める構文へ整理する必要があります。

## 複数リソースの出力

リソースごとに`emit`を繰り返すと、出力対象が多いファイルで同じ構文が連続します。複数の値を明示的に列挙できる`emit:`ブロックがあると、暗黙のList flattenを追加せずに出力宣言をまとめられます。

## 単一YAMLドキュメントの読み込み

YAMLファイルをデータとして読む場合に`manifest.load(...)[0]`を使うと、単一ドキュメントを読み込む意図が表現されず、複数ドキュメントも先頭だけを黙って選択します。単一ドキュメントを直接返し、複数ドキュメントではエラーにする構造化YAML importが必要です。

## リソース識別子による置換

特定のKubernetes ResourceをListからfilterして差し替えると、対象が存在しない場合も成功し、`apiVersion`、`namespace`などのidentityを指定しない実装が生じます。完全なidentityで対象を指定し、未存在または重複をエラーにする明示的な置換操作が必要です。

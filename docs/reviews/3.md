## 結論：Go/WASMは維持し、Browser SDKの実装を大幅に整理するのがよいです

[manifest-configuration-language/mcl の packages/browser](https://github.com/manifest-configuration-language/mcl/tree/main/packages/browser?utm_source=chatgpt.com) を確認しました。

現状の最大の問題は、Go/WASMではなく、それを扱うJavaScript側で独自のWorker通信・ライフサイクル管理を大量に実装していることです。

私なら、次の構成に変更します。

- TypeScript：JavaScriptと手書きの型宣言を統合する
- Comlink：独自のWorker RPCを置き換える
- p-queue：既存の優先度付き実行キューを維持する
- Go/WASM：MCLの実行エンジンはそのまま利用する
- TypeScript Compiler (`tsc`)：型検査・JS出力・型宣言生成を標準ツールで行う

大切なのは、単にファイルを分割することではありません。独自実装そのものを減らし、必要な状態管理だけを残すことです。

ただし、Comlinkに変更しても、実行中のWASMを強制停止する処理や、Worker再生成後のプロジェクト復元は必要です。ここまで削除すると、現在の安全性や機能が損なわれます。

### 特に改善すべき3点

① Worker通信を独自実装している

現在、`startWorker()`、`syncProjectToWorker()`、`execute()` がそれぞれメッセージリスナー、要求ID照合、Promiseのresolve/reject、エラー処理、cleanupなどを扱っています。

これは典型的なRPCの仕事です。Comlinkなら呼び出しとレスポンスの対応付けをライブラリ側に任せられます。

GitHub

② Browser SDKに2種類のAPIが存在する

現在は `runtime.render(source, files)` と `project.render()` のように、ソース単位とプロジェクト単位のAPIが並立しています。

内部では最終的に同じ `execute()` に集約されるのに、引数解釈・オーバーロード・検証コードが増えています。

MCLは複数ファイルやimportを扱う言語なので、Project APIへ一本化する方が自然です。

③ website側にも重複した抽象化がある

[`website/src/playground/apiClient.ts`](https://github.com/manifest-configuration-language/website/blob/main/src/playground/apiClient.ts?utm_source=chatgpt.com) に約320行のBrowser SDKラッパーがあります。

ここで再び `lint`、`complete`、`definition`、`hover`、`rename` などの引数とエラーを変換しています。

両者を連携して整理すれば、Browser SDKだけでなくPlayground側の保守コストも削減できます。

## 2. 推奨する新しいアーキテクチャ

UIとWASM間の通信をComlinkに任せ、MCL固有の処理だけをSDKに残します。

### Comlinkで削除できるコード

現在の `requestId` によるメッセージ照合、Workerイベントリスナーの登録・解除、`response` と `project-updated` の振り分けは、ComlinkのRPCに置き換えられます。

Worker側は概念的に次のようなAPIだけを公開すれば十分です。

```

import { expose } from "comlink";

const api = {
  async initialize(assets: RuntimeAssets): Promise<void> {
    // Go/WASMのロードと初期化
  },

  updateProject(
    id: string,
    update: ProjectDelta,
    binaries: Record<string, Uint8Array>,
  ): WasmResponse {
    return JSON.parse(
      globalThis.mclWasm.updateProject(
        id,
        JSON.stringify(update),
        binaries,
      ),
    );
  },

  run(
    request: WasmRequest,
    binaries: Record<string, Uint8Array>,
    projectId?: string,
  ): WasmResponse {
    return JSON.parse(
      globalThis.mclWasm.run(
        JSON.stringify(request),
        binaries,
        projectId,
      ),
    );
  },
};

expose(api);
export type WorkerApi = typeof api;

```

これは設計例であり、実際にはGoブリッジの初期化やエラー処理も含めて実装します。

メインスレッドからは `Comlink.wrap<WorkerApi>(worker)` を使い、普通の非同期関数として呼び出せます。

また、バイナリは `Comlink.transfer()` によってコピーではなく転送できます。現状と同様に、呼び出し元が保持する `Uint8Array` は保護する必要があります。

### TypeScriptによる型の一本化

現在の `index.js` と `index.d.ts` の二重管理はやめます。

`src/index.ts` などを正規の実装として、`tsc` でJavaScriptと公開型宣言を生成します。TypeScriptには標準で `.d.ts` の生成機能があります。

[image](https://www.google.com/s2/favicons?domain=https://www.typescriptlang.org\&sz=32)

typescriptlang.org

ここでは `tsup`、`tsdown`、Rollupなどを無条件に追加する必要はありません。

まずは `tsc` だけで済ませるのが最も単純です。Workerを別ファイルとして出力し、既存のVite互換Worker構築方式を維持します。Viteは `new Worker(new URL(..., import.meta.url))` を公式にサポートしています。

## 3. API自体もシンプルにする

私はBrowser SDKの公開APIにも破壊的変更を加える価値があると考えます。

現在の `parse`、`lint`、`format`、`check`、`evaluate`、`render` などを個別に公開する方式は分かりやすい一方、同じ処理を何度もラップしています。

推奨するのは、型安全な共通 `run()` を中心にする設計です。

### 提案する新API

```

const runtime = createMclRuntime();

try {
  await runtime.warmUp();

  let project = runtime.openProject({
    "main.mcl": source,
    "values.json": JSON.stringify(values),
  });

  const result = await project.run("render", {
    entrypoint: "main.mcl",
    priority: "interactive",
  });

  console.log(result.yaml);

  project = project.patch({
    set: { "main.mcl": nextSource },
  });

  const diagnostics = await project.run("lint");
} finally {
  runtime.dispose();
}

```

`project.patch()` は新たに提案するAPIです。現行の `update()` と異なり、変更のあったファイルだけを受け取ります。

型システム側では、`run("render")` は `RenderResult`、`run("lint")` は診断結果、`run("completion")` は位置指定必須、という形でコンパイル時に制限できます。

これにより、操作ごとのラッパーやオーバーロードを削減でき、`website` 側も同じAPIを直接使いやすくなります。

## 4. パフォーマンス面で特に重要な改善

プロジェクト同期の改善

優先度高

現在の `createProjectSnapshot()` は、更新時にファイルの内容を比較します。`Uint8Array` は変更がないかバイト単位で走査するため、巨大なバイナリファイルを含むプロジェクトでは、ソースコードを少し変更しただけでも比較コストが発生します。

しかも `website` 側は操作のたびにプロジェクト全体のファイル集合を渡しています。

これを差分ベースの `patch()` と、構造共有する不変スナップショットに変えると、変更されていないバイナリを毎回走査する必要がなくなります。

Worker再起動後の復元

維持必須

実行中のGo/WASMは、メインスレッドからのAbortSignalだけでは直ちに中断できません。

キャンセルやタイムアウト時にはWorkerを終了し、次回起動時に最新のプロジェクトスナップショットを復元する仕組みを残す必要があります。

キュー管理

既存ライブラリ維持

`p-queue` は既に導入されており、優先度、並列度1、待機中のAbortを扱えます。これは置き換えなくてよいです。

ただしキューのタイムアウトだけでは実行中の処理は確実に停止しないため、Worker終了の制御はSDK側で持ちます。

## 5. 安全性について修正したい点

コードを確認して、保守性以外にも改善したい点がありました。

| 箇所 | 問題・リスク | 対応 |
| ------------------------ | ------------------------------- | ------------------------------------------------ |
| Worker正常起動後 | 待機中の予期しないWorkerエラーを常時監視する構造ではない | Workerセッションの存続期間全体で `error` / `messageerror` を監視 |
| `worker.js` の `go.run()` | 初期化完了後の異常終了が確実に通知される設計ではない | Goランタイム終了を監視し、異常終了時にはセッションを破棄 |
| ネットワーク遮断 | JavaScriptのネットワークAPIを上書きしている | API上書きだけをセキュリティ境界と考えず、Go側の入力制限・配信時CSPなども維持・強化 |
| プロジェクトファイル | 参照共有や差分更新を誤ると、古い内容を実行しうる | 不変スナップショットとWorker同期済みrevisionを管理 |
| エラー処理 | 複数箇所で類似のPromise・エラー変換処理を持つ | RPC境界で一元化 |

ネットワーク制限については注意が必要です。現在の実装はAPI上書きで防御していますが、これは汎用的なセキュリティサンドボックスではありません。

一方、MCLは任意のJavaScriptを実行する仕組みではないため、外部ランタイムへの全面移行よりも、Go側の安全なファイルシステムと入力制約を維持する方が合理的です。

## 6. 最終的に目指すファイル構成

```
packages/browser/
├── src/
│   ├── index.ts          # 公開API・型のexport
│   ├── runtime.ts        # キュー・Worker lifecycle
│   ├── project.ts        # スナップショット・差分
│   ├── worker.ts         # Comlink + Go/WASM bridge
│   ├── protocol.d.ts     # JSON Schemaから生成
│   └── limits.ts         # Schemaから生成
├── scripts/
│   ├── build-wasm.mjs
│   └── generate-protocol.mjs
├── test/
│   └── runtime.test.mjs
├── tsconfig.json
├── package.json
└── README.md
```

これはファイル数を最小化するというより、各ファイルの責務を明確にし、重複する処理を消す設計です。

`generate-protocol.mjs` はGo側の定数生成も担当しているため、単純に削除するべきではありません。JSON Schemaを単一の定義元とする方針は維持します。

また、Go標準の `wasm_exec.js` はWASMをビルドしたGoに対応したものが必要なので、現在のビルドスクリプトがそれを一緒にコピーしている設計も維持します。

## 7. 実装方針の最終判断

| 変更                             | 判断   |
| ------------------------------ | ---- |
| JS → TypeScript                | 採用   |
| 独自Worker RPC → Comlink         | 採用   |
| p-queue                        | 維持   |
| Source APIとProject APIの一本化     | 採用   |
| プロジェクト差分更新API                  | 採用   |
| 手書き `.d.ts`                    | 廃止   |
| JSON Schemaからのプロトコル生成          | 維持   |
| Go/WASM → TinyGo / Rust / WASI | 不採用  |
| 独自ビルドツールの追加                    | 原則不要 |
| Worker Pool化                   | 不採用  |
| 既存のタイムアウト・キャンセル・復元機能           | 維持   |

実装時には、現在のユニットテストで確認されているキャンセル・再初期化・バイナリ保護に加えて、Worker異常終了、古いスナップショット、差分同期の整合性をテストするべきです。UIのE2Eテストを新設する必要はありません。

特に重要なのは、Comlink導入だけで終わらせず、Project APIとスナップショット管理も一緒に設計し直すことです。 これならコードの単純化と実行性能の改善を両立できます。

なお、今回はリポジトリのコードを調査して設計を提示した段階であり、GitHub上のファイルはまだ変更していません。実際の削減行数や速度改善量も未計測です。
